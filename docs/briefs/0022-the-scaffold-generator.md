## Why a generator, and why one whose output is already green

The plan sentence was written when the gate was small. It is not small now: forty-three rules in
[`rules/ledger.yaml`](../../rules/ledger.yaml), and a hand-written backend feature has to be right about a
unit registration, an allowed-edge list, a guard declaration, two test tiers, a coverage floor, two
snapshots, two counted claims, a fan-in baseline and a `git add` early enough for the index to see anything
at all.

Those obligations are not equally loud. Forgetting the formatter costs four seconds. Forgetting the guard
declaration is the one that matters, and `RULE-SEC-001` exists precisely because its failure mode is silent:
the route works, it just works for everybody.

The obvious way to build this — a template directory with `TODO` and `pass` in it — would have made things
worse. A contributor would still have the same forty-three obligations and would now also believe the tool
had handled them. So the acceptance criterion was taken literally: what comes out has to be green with
nothing edited, and if it is not, the generator is wrong, not the criterion.

## What it emits

`KIND=backend-feature NAME=reports` writes five files and edits five:

| Written | Why it is not a placeholder |
|---|---|
| `backend/app/routers/reports.py` | one real `GET /reports`, guarded by `get_current_user`, with a structured log line that satisfies `RULE-OPS-002` |
| `backend/app/services/reports_service.py` | the logic, reachable without a client |
| `backend/app/reports_models.py` | the shapes, beside `models.py` rather than inside the shared DTO kernel |
| `backend/tests/unit/test_reports.py` | six tests over the whole slice — a new module with no tests is the single most likely way to fail `RULE-TEST-003` on an axis unrelated to the change |
| `backend/tests/container/test_reports.py` | proof that the module is in the shipped image, which is the one thing this tier can say about a feature that touches no binary |

and edits [`architecture.toml`](../../architecture.toml) (the unit, its edge list, and its id in the `to`
lists of `be/app` and `tests`), [`rules/route-guards.toml`](../../rules/route-guards.toml),
[`backend/app/main.py`](../../backend/app/main.py), [`AGENTS.md`](../../AGENTS.md)'s two counts, and
[`ops/structure-baseline.toml`](../../ops/structure-baseline.toml) when a hub moved. Then it runs `make fix`,
`./run surfaces --update`, `git add` and an index rebuild, in that order, because each step invalidates the
one before it.

`KIND=frontend-feature` writes the view, its pure logic module and a vitest file, registers `fe/<name>` with
edges to `fe/shared` and `fe/layout` only, and adds the SPA route.

## The unit is a vertical slice, and its position in the file is load-bearing

`be/feature/<name>` owns all three backend files, and its edge list withholds `be/adapters/task`. That is
the plan's "inherits every applicable boundary rule" made specific: the rule the generated unit inherits is
*narrower* than the layer it enters at, so a generated feature cannot reach the Taskwarrior subprocess
except through `be/services`, where the validation lives.

Ownership resolves to the first unit whose patterns match, and `be/routers` claims
`backend/app/routers/**` by glob — so generated units are declared at the top of the units section, between
markers, and the file says why. Narrowing `be/routers` to an explicit list was the alternative and it is
worse: it would silently unown the next hand-written router, and an unowned file is not a gate failure.

What the checker does **not** see is the router/service split inside the slice. Both files are in one unit,
so the import between them is internal. That is written into the generated unit's own `note`, because the
reader who is told a boundary is enforced when it is not is worse off than the one who is told nothing.

## The acceptance criterion, run rather than asserted

`./run scaffold KIND=backend-feature NAME=reports` in a clean tree, then `./run verify` immediately,
touching nothing:

```
  route-guards
  ok    32 route(s) declared; every guard matches the code
  surfaces
  ok    5 surface snapshot(s) match; every env var is read and documented
  contract
  ok    contract claims hold; ledger complete; no expired waivers; no orphan suppressions
  boundaries
  ok    2 declared cycle(s) inventoried, 0 new, 0 forbidden edges, 0 hub regressions, 0 restricted imports
      46 rule(s) proven able to fail, 0 not

```

The same for `KIND=frontend-feature`, with `48 passed (48)` on the frontend tier against 42 before. Both
were then removed with `git checkout` and `rm`, and `verify` is green again with `git status` clean — a
generator whose output cannot be taken back out is a trap, and the removal is part of the acceptance, not an
afterthought.

The first backend run was **not** green, and the finding is worth recording because it is exactly what this
step is for: `RULE-ARCH-003` failed with `backend/app/dependencies.py` fan-in rose to 7, baseline 6. Every
guarded route imports `get_current_user`; a feature that adds one is one more dependent on the auth choke
point. [ADR 0029](../adr/0029-the-scaffold-generator.md) argues the resolution — raise the number, in the
diff, with a dated line naming the command — and rejects the alternative of allowlisting the file, which
would drop the signal permanently for every future dependent including the ones worth looking at.

## What it deliberately does not do

It does not design the feature, it does not write this document (that needs intent; `./run brief` pre-filled
the facts above and left the rest as TODOs), and it does not commit — it stages, because the index reads
`git ls-files` and an unstaged file is invisible to ownership, boundaries and the counted claims, which is
how a local `verify` passes on a tree CI fails on.

It also does not remove what it generated. Every edit it makes is to a tracked file and every addition is a
new file, so removal is `git checkout` plus `rm`; the by-hand recipe for a tree with other work in flight is
in [`docs/task-interface.md`](../task-interface.md). A `--remove` flag was considered and rejected in
[ADR 0029](../adr/0029-the-scaffold-generator.md): a second code path over the same nine files, exercised
roughly never.

## Behaviour change

None in the application. One command changes from exiting `3` with "not implemented yet" to doing the thing
it always said it would do, which is the only behaviour change in the diff.
